A Base is a saved, non-owning view over pages in a vault. Its `.base.toml` definition owns a membership predicate, advisory property schemas, and one or more saved table views; it never owns the matching rows. The pages remain ordinary Markdown files and may match any number of Bases: a Base does not move, copy, or own them.

## Prerequisites

Start Clepsydra with an initialized vault and at least one Markdown folio whose
TOML frontmatter contains fields worth filtering or displaying. Use `/bases`
for guided authoring. Manual definitions must be direct children of
`<vault>/bases/`, end in `.base.toml`, and contain valid TOML with a `name`.

## Workflow

Create a Base, define its membership predicate and advisory property schemas,
configure one or more saved table views, preview the draft, then save against
the revision you loaded. Open `/bases/<slug>` to query the saved view, edit
frontmatter properties or relation values inline, add a matching member, or
embed the non-owning view in a Folio. The following sections specify the
definition format and each authoring path.

## Create and configure a base

Open `/bases` from the **Bases** header item or run **Open Bases** in the command palette. The index lists saved bases and files that need repair. Choose **Create base**, or run **Create Base** in the command palette, to open guided creation. Enter a name and slug, optionally define the first membership rule, and create the base. Clepsydra opens `/bases/<slug>/edit` with an `All` table view and `title` column ready to configure.

The Configure workspace has five sections:

- **General** changes the displayed name and description.
- **Filter** builds base membership from comparison, all, any, and not rules.
- **Properties** declares ordered advisory property schemas and their options.
- **Preview properties** chooses the ordered, optionally labelled fields used by generic page previews.
- **Views** configures ordered table views, their extra filters, columns, display labels, sorts, grouping, and aggregates.

Changes remain a local draft until you explicitly choose **Save**; there is no autosave. **Discard** restores the last loaded revision. Leaving with unsaved changes opens a confirmation, and closing the browser is guarded by the browser's unsaved-change prompt. Every Save includes the revision that was loaded. If the file changed in another editor or Clepsydra session, Save retains the local draft and reports a conflict instead of overwriting the newer file. Reload the changed definition before deliberately reapplying or discarding the draft.

The live preview evaluates the unsaved membership or selected view after a 250 ms pause. It is read-only, returns at most 100 preview rows, retains real totals in group headings, and does not move keyboard focus when results refresh. Structural, evaluation, and network failures are shown beside the preview; a preview network failure alone does not disable Save.

## Minimal working example

Place a page under `<vault>/books/` (for example, `<vault>/books/the-book-of-the-new-sun.md`) with this TOML frontmatter:

```toml
+++
title = "The Book of the New Sun"
kind = "BOOK"
author = "Gene Wolfe"
status = "reading"
rating = 4.5
started = 2026-07-30
+++
```

The `books/` folder makes the page's resolved system `kind` equal to `BOOK`. In page frontmatter, `kind` itself is an ordinary property; the explicit system key is `type = "BOOK"`. A page elsewhere in the vault therefore needs `type = "BOOK"` to match the system-field filter below. See [System fields and field names](#system-fields-and-field-names) for the distinction.

The guided editor writes this base file. For reference—and as an advanced manual escape hatch—the equivalent TOML is:

```toml
# <vault>/bases/reading.base.toml
name = "Reading Log"
description = "Books in flight and their wake."
preview = [
  { field = "title", label = "Book" },
  { field = "author" },
  { field = "body", label = "Excerpt" },
]

[filter]
field = "kind"
op = "eq"
value = "BOOK"

[properties]
author = { type = "text" }
status = { type = "select", options = ["queued", "reading", "finished", "abandoned"] }
rating = { type = "number" }
started = { type = "date" }

[[views]]
name = "Continues"
layout = "table"
filter = { field = "status", op = "eq", value = "reading" }
sort = [{ field = "started", dir = "desc" }]
columns = ["title", "author", "rating", "started"]
labels = { title = "Book", author = "Writer" }
```

The filename `reading.base.toml` gives the base the slug `reading`, so its web UI is `/bases/reading`. The base membership filter selects books, and the saved view adds the `status = "reading"` filter. The root `preview` list supplies generic link and inactive-tab previews; its `author` entry demonstrates that `label` is optional. The view's `labels` table changes only its rendered column headings. The base owns no pages; deleting `reading.base.toml` deletes neither the matching pages nor their properties.

## File location and slug

Base definitions live at:

```text
<vault>/bases/<slug>.base.toml
```

Only files ending in `.base.toml` in that directory are loaded. The filename stem is the API and UI identity: `deep-work.base.toml` has slug `deep-work` and UI path `/bases/deep-work`.

A base requires `name`. `description`, `filter`, `properties`, `preview`, and `views` are optional, although the web UI needs at least one view to display a table. With no membership `filter`, the base matches every indexed page.

## Page properties and advisory schemas

The `[properties]` table describes keys stored in page frontmatter; it does not create separate records or storage. Values retain their native TOML types when indexed. A declaration controls typed filtering, grouping, inline editors, LSP completions, and diagnostics for every matching page that carries the key.

Schemas are advisory. A page whose value disagrees with a declaration still indexes, and the declaration does not rewrite or reject it. Clepsydra reports a warning instead. Likewise, a non-empty `options` list constrains diagnostics and completions rather than blocking an unfamiliar value, and `many = false` on a relation warns about multiple targets rather than enforcing a write constraint. An empty `options` list means an open vocabulary: the LSP can offer values already observed in the vault and does not warn about new ones.

## Property types

| Type | Page frontmatter value | Schema details |
| --- | --- | --- |
| `text` | TOML string | Free text. |
| `number` | TOML integer or float | Uses numeric filtering, sorting, and aggregates. |
| `bool` | TOML boolean (`true` or `false`) | Edited as a boolean in the table UI. |
| `date` | Unquoted TOML date, such as `2026-07-30` | Quoting the date turns it into text and produces a warning. |
| `datetime` | Unquoted TOML date-time | Use a TOML date-time such as `2026-07-30T14:30:00Z`. |
| `select` | One TOML string | `options = [...]` declares the vocabulary; an empty list is open. |
| `multi_select` | An array of TOML strings | `options` has the same advisory behavior as `select`. |
| `url` | TOML string | Uses the text editor in the table UI. |
| `relation` | A string or array of strings, normally wikilinks such as `"[[Solar Cycle]]"` | `many = false` advises one target; relations participate in link resolution. |

These are the complete shipped type tokens: `text`, `number`, `bool`, `date`, `datetime`, `select`, `multi_select`, `url`, and `relation`.

## System fields and field names

The built-in system fields are:

```text
id, path, title, kind, project, tags, aliases, created_at, updated_at, encryption, journal_date, word_count
```

They can all be used in columns and with their supported filter operators without property declarations. Bare and `sys.`-prefixed scalar names are materialized under the exact requested column key, so `kind` produces a `kind` column and `sys.kind` produces a `sys.kind` column. Scalar system fields can also be used for sorting except `encryption`; `tags` and `aliases` are also non-sortable because they are multi-valued. A bare field name resolves system-first, so `kind` means the resolved page kind and `prop.kind` means a raw page property named `kind`. The `sys.` and `prop.` prefixes disambiguate field references in filters, columns, sorts, grouping, and aggregate field references.

If a page has an extra key whose name collides with a system field, address it as `prop.<name>`. Declaring that colliding key in `[properties]` produces a shadowing diagnostic.

The system `kind` comes from the page's `type` frontmatter key, or from its top-level folder when `type` is absent. This is why the minimal example under `books/` matches `field = "kind"` even though its extra `kind` property is not the system field.

## Presentation labels and generic page previews

Presentation metadata changes what readers see, never the identity or stored value of a field. The two presentation controls are independent:

- A view's `columns` chooses the fields in that saved table. Its `labels` map overrides headings for that view wherever the table is rendered, including Base embeds. A label can be configured before its field is added to `columns`, but it appears only when that field is rendered. It does not rename the column, its sort/query/edit key, or the corresponding page-frontmatter key.
- The root `preview` array is an ordered projection for generic page previews opened from path-backed links and inactive Folio tabs. It neither adds columns to a saved view nor inherits a selected view's columns or labels.

This is the exact TOML shape:

```toml
preview = [
  { field = "title", label = "Book" },
  { field = "author" }, # label is optional
  { field = "body", label = "Excerpt" },
]

[[views]]
name = "Continues"
columns = ["title", "author", "status"]
labels = { title = "Book", author = "Writer", status = "Reading state" }
```

Omitting a preview row's `label` uses that field's canonical output key as its display label. Do not write an empty string instead: a blank `preview.field`, an explicitly present blank or whitespace-only preview label, and a blank or whitespace-only `views.labels` value are validation errors.

Presentation references use the same system-first identity rules as other Base fields. `title` and `sys.title` identify the same system field, while `prop.title` identifies a custom page property named `title`. An ordinary non-system key such as `author` is already a custom property. If a custom key itself starts with the reserved `prop.` or `sys.` grammar prefix, add an explicit `prop.` qualification: `prop.prop.title` identifies a custom key literally named `prop.title`, and `prop.sys.custom` identifies one literally named `sys.custom`. Quote dotted keys in a TOML label map, for example `labels = { "prop.title" = "Frontmatter title" }`.

Equivalent spellings share one canonical identity. A `preview` list cannot repeat one identity—for example, it cannot contain both `title` and `sys.title`. Labels are resolved by identity when rendered, but the configured column and property keys remain unchanged. The guided editor disables duplicate choices and writes the required explicit qualification rather than guessing.

`body` is a reserved, read-only presentation field, not a declarable property. Use the canonical spelling `body`; its accepted presentation aliases resolve to the same identity. It cannot be filtered, sorted, grouped, aggregated, or edited. Generic previews show a normalized, bounded Markdown excerpt (up to 240 Unicode characters and clamped to two lines); an empty normalized excerpt is missing.

For a page that matches more than one Base, Clepsydra sorts those Bases by slug, then walks each Base's `preview` rows in their configured order. The first occurrence of a canonical identity fixes its position. Later occurrences add source provenance without moving or duplicating the field. System and body keys remain bare; a custom key is explicitly `prop.`-qualified in the merged output when it shadows a system name or starts with `prop.` or `sys.`, so distinct identities never collapse.

An omitted preview label falls back to that canonical output key. If every contributing Base has the same effective label, the merged field uses it. If they disagree, the card falls back to the canonical key and shows `!` for the label conflict. If matching Bases declare incompatible schemas for a custom property, its current raw value remains readable in this read-only projection and the card shows `≠`; no editor schema is chosen. An absent value renders as an em dash (`—`). Only the first four merged fields render, in deterministic order, followed by `+N more` for the exact remainder.

Protected pages return an empty Base preview projection. Link and tab cards suppress the whole projected-property region—including cached values, conflict markers, remainder counts, and projection-error copy—and show the protected-page state instead.

## Membership and saved-view filters

A comparison filter has `field`, `op`, and usually `value`:

```toml
[filter]
field = "rating"
op = "gte"
value = 4
```

The operators are:

| Operator | Meaning and restrictions |
| --- | --- |
| `eq` | Equal to a compatible scalar value; on multi-valued fields, matches membership. |
| `ne` | Not equal; on multi-valued fields, no element may equal the value. Missing properties also match. |
| `lt`, `lte`, `gt`, `gte` | Ordering comparisons. For declared properties, use only `number`, `date`, or `datetime`. |
| `contains` | Substring match on text; exact membership on multi-valued values such as `multi_select`, `tags`, and `aliases`. |
| `in` | Matches any candidate in an array, for example `value = ["queued", "reading"]`. |
| `links_to` | Relation target match by page UUID or canonical name. Use with `relation` properties. |
| `is_empty` | The field is absent or empty. Omit `value`; it has no meaningful value. |
| `not_empty` | The field is present and non-empty. Omit `value`; it has no meaningful value. |

`contains` is also an exact match for declared `select` and `relation` values. Ordering a declared non-orderable type produces a diagnostic and the view query can fail when an operator or value is incompatible with its field.

### Boolean filters

Filters compose with `all` (every child), `any` (at least one child), and `not` (negate one child). For nested filters, TOML arrays of tables are easier to read than deeply nested inline tables:

```toml
[[filter.all]]
field = "kind"
op = "eq"
value = "BOOK"

[[filter.all]]
  [[filter.all.any]]
  field = "status"
  op = "eq"
  value = "reading"

  [[filter.all.any]]
  field = "status"
  op = "eq"
  value = "queued"
```

The equivalent shape is “kind is BOOK AND (status is reading OR queued).” An inline `not` is useful for one predicate:

```toml
filter = { not = { field = "status", op = "eq", value = "abandoned" } }
```

A base's membership filter and a selected view's filter are always ANDed. A view filter narrows membership; it cannot add a page that the base filter excluded.

### Tag conditions

`tags` and `aliases` are multi-valued, so the three predicates authors actually
want are spelled with the operators above rather than with a separate condition
language:

| Predicate | Filter |
| --- | --- |
| has all of `beer`, `tasting` | `all` of one `contains` per value |
| has any of `beer`, `wine` | one `in` over the list |
| has none of `beer`, `wine` | `not` around the any-of filter |

```toml
# has all of
[[filter.all]]
field = "tags"
op = "contains"
value = "beer"

[[filter.all]]
field = "tags"
op = "contains"
value = "tasting"

# has any of
filter = { field = "tags", op = "in", value = ["beer", "wine"] }

# has none of
filter = { not = { field = "tags", op = "in", value = ["beer", "wine"] } }
```

A single value needs no quantifier: `{ field = "tags", op = "contains", value = "beer" }`
is the same predicate under all-of and any-of alike.

In the UI these author as one condition row — field, quantifier, and tag chips
with suggestions from the vault — for every one of those shapes, however the
file spells them. The row rewrites only the condition you edit, so opening and
saving a base leaves its other filters byte-identical. Two shapes stay with the
general condition row: `tags is_empty` / `not_empty`, and a negated all-of
group, which means "not both" rather than "neither". Any tag row can be
switched to that general row from its own controls.

## Title templates

A Base may propose titles for the members created through it:

```toml
name = "Reading"
title_template = "{author} — {work}"
```

Each `{field}` interpolates that field from the member draft as it is filled;
a placeholder with no value yet contributes nothing, and separators left
dangling around it are trimmed, so a half-filled draft still proposes a
sensible title. Placeholders name declared properties or system fields —
anything else is a validation error, because nothing would ever fill it. The
proposal stops the moment the author types a title of their own, and the
resolved title is always visible before creation, since it determines page
identity and the canonical path.

## Views: columns, sorting, grouping, and aggregates

Each `[[views]]` entry is a saved view. Its fields are:

- `name`: required and unique within the base.
- `layout`: `table` is the only shipped layout and is the default.
- `filter`: an optional additional filter, ANDed with base membership.
- `columns`: field names in display order. The web UI falls back to `title` when this is empty.
- `labels`: per-field display headings for this view. Dotted field keys must be quoted in TOML. Labels do not change `columns` or any data key.
- `sort`: an ordered list of `{ field, dir }` keys. Directions are `asc` and `desc`; omitted `dir` defaults to `asc`. Equal values use page path as a stable tie-breaker.
- `group_by`: a grouping field.
- `aggregates`: aggregate calculations shown with grouped results.

Use a property in `group_by` only when it is declared. Groupable property types are `select`, `text`, `bool`, `date`, `datetime`, and `url`; scalar system fields such as `kind` are also groupable. `number`, `relation`, and `multi_select` properties are not groupable.

The shipped aggregate functions are `count`, `sum`, `avg`, `min`, and `max`. `count` needs no field. The other functions require a compatible declared `number`, `date`, or `datetime` field (or the numeric system field `word_count`). Aggregates are returned with grouped results. For example:

```toml
[[views]]
name = "By status"
layout = "table"
group_by = "status"
aggregates = [
  { fn = "count" },
  { fn = "avg", field = "rating" },
]
sort = [{ field = "started", dir = "desc" }]
columns = ["title", "author", "rating", "started"]
```

## Web UI, saved tables, and inline editing

Open `/bases` to discover, create, configure, open, or delete bases. Open `/bases/<slug>` for a saved table. The UI selects the first view initially and presents the other saved views as tabs. It renders flat or grouped tables, resolves the active view's display labels by canonical field identity while retaining the original field keys, shows group counts and aggregate values, and lets you click a column header to apply a temporary ascending or descending sort override. **Configure** opens `/bases/<slug>/edit`. Clicking a title opens that page.

System fields and undeclared columns are read-only. A column backed by a declared property opens a type-specific inline editor: text/URL, number, boolean, date, date-time, select, multi-select, or relation. Relation editing accepts comma-separated targets and writes wikilinks; single-target entry offers page-title suggestions.

Each commit fetches the page's current revision, sends only the changed property key with its type hint, and updates `updated_at`. For TOML `+++` frontmatter, the server splices that edit into the existing bytes, preserving untouched keys and comments. The first inline property edit on legacy YAML `---` frontmatter instead converts it to TOML through full serialization, so YAML frontmatter comments are not preserved. A stale edit is rejected rather than overwriting a newer page revision; the table refetches the winning state and reports the failed key.

### Add members inline

Choose **Add member** in a saved table view to open one temporary row. This creates a new page; it does not enroll an existing page in the base. Enter a title and the visible or filter-required properties, then choose **Save** or press <kbd>Ctrl</kbd>/<kbd>Cmd</kbd>+<kbd>Enter</kbd>. Clepsydra creates the Markdown page only when its metadata matches both the base membership filter and the active view filter. A rejected row remains editable and creates no file.

After a successful save, the new title link receives focus and the row moves from its temporary position to its authoritative sort and group position.

Press <kbd>Escape</kbd> to cancel after any open field editor has closed. Derived filters that an empty page cannot satisfy—for example, `word_count > 0`—disable **Add member** and explain the blocking constraint. Create the page in Folio when initial body content is required.

Renaming or removing a property declaration changes only the base schema. It does not rename or remove that key in existing page frontmatter. Deleting a base removes only its `.base.toml` definition: all matching Markdown pages and all of their properties remain.

## Embed a Base in a Folio

A Base embed is a live, non-owning view of the same pages as its saved Base. The Folio stores only the Base/view reference and document-local filter, sort, and limit. It does not copy the Base definition, table rows, or member pages into the Folio.

In a Folio editor, open the slash-command menu and choose **Base embed**. The structured **Edit Base embed** inspector opens immediately. Select a Base and one of its saved views, then optionally build an additional nested filter, arrange ordered sort keys, and set a row limit. Choose **Save** to replace the new block with the configured live table; **Cancel** removes a new unconfigured block or leaves an existing configured block unchanged.

The saved Folio Markdown contains a fenced `base` block. This is a complete valid example:

````markdown
```base
base = "reading-log"
view = "Currently reading"
filter = { field = "rating", op = "gte", value = 4 }
sort = [{ field = "rating", dir = "desc" }]
limit = 20
```
````

Normal configured embeds are not edited as raw source. Use **Edit embed** and the structured inspector; raw TOML editing appears only when repairing an invalid fence. Saving a valid configuration writes canonical TOML with the keys in `base`, `view`, `filter`, `sort`, `limit` order.

An omitted embed limit has an effective default of 50. Explicit limits accept 1 through 200. A flat table applies the limit to its total returned rows; a grouped table applies it to each group while preserving the true group totals and aggregates. The rendered block reports when rows were capped.

An omitted `sort` inherits the saved view's ordered sort. An explicit `sort = []` removes saved-view sorting without inheriting it. Switching saved views keeps the embed filter and limit but resets sort to inherited for the new view. Changing the Base selects its first view, clears filter and sort, and keeps the limit. Clicking a sortable table header replaces any ordered override with that one column and direction. These Base/view/sort changes update only this Folio block and survive reload.

The embedded table keeps the normal Base table controls. A title opens its member Folio, and declared properties use their type-specific inline editors. Property edits write the member page, not the Folio block. **Add member** is available only when the current Base membership, saved-view filter, and embed filter can be satisfied by a new page. Its draft includes fields required by all three scopes. A successful save creates one member page atomically; if the configured row cap excludes that matching page, the block keeps the success, leaves the updated cap notice visible, and does not try to focus a row that was not returned.

Missing references remain in the document. A missing Base shows its slug with **Edit embed** and **Remove**; a missing or renamed view can be replaced from the inspector. Malformed or otherwise invalid `base` fences preserve their original bytes and open the inspector in source-repair mode. Invalid repairs stay local, and saving valid TOML replaces the recovery source with one canonical configured block.

The embed is one Slate block with explicit keyboard boundaries:

- Select the block and press <kbd>Enter</kbd> or <kbd>F2</kbd> to enter its first enabled view/table control, falling back to **Edit embed** and then **Remove**.
- Press <kbd>Tab</kbd> through the embedded controls to leave at the Slate point after the block; <kbd>Shift</kbd>+<kbd>Tab</kbd> through the first control leaves before it.
- Press <kbd>Escape</kbd> to leave after the block unless a cell editor, dialog, or other nested control handled the key first.
- Press <kbd>Backspace</kbd> or <kbd>Delete</kbd> to remove the selected block only while the Folio editor owns focus. Focus moves to the following text point, or the preceding point when necessary.
- Cancelling or pressing <kbd>Escape</kbd> in the inspector returns focus to **Edit embed** for an existing block.

The structured editor is the normal authoring path, but the TOML format remains public and editable. Manual TOML is useful for advanced changes or recovery; use the exact `preview`/`labels` shapes and qualification rules above. Guided saves structurally merge managed presentation nodes, preserve comments and unknown keys when they can be retained safely, and reject a removal that would silently discard an attached comment. A valid manual edit made while Configure is open changes the file revision, so the next Save reports a conflict and preserves the local draft; reload before reapplying it. If a definition cannot be parsed, `/bases` reports it under **Base files needing repair** and provides its path. Repair that file in a text editor, then reload; Clepsydra never fabricates a replacement draft over an unparseable file.

## Neovim/LSP completions and warnings

With `clep lsp` attached, completion inside a page's `+++` frontmatter offers property keys declared by bases. Properties from bases that match the current page rank first. Quoted values for `select` and `multi_select` complete from declared options; an open vocabulary can complete from observed vault values. Typing `[[` in a relation value uses normal wikilink completion.

For matching bases, the LSP warns about incompatible native TOML types, values outside a non-empty select vocabulary, multiple relation values when `many = false`, and missing relation targets. It does not diagnose an ambiguous relation target as ambiguous: ambiguity still appears as `invalid_relation_target` in Reference Repairs. These are warnings, never indexing errors. Legacy `---` frontmatter does not receive property-schema diagnostics. The LSP completes and checks page frontmatter; it does not provide an editor for `.base.toml` files.

See [LSP setup and troubleshooting](/docs/lsp) for client configuration and the complete language-server capability list.

### Relation repair

Relation values participate in the same canonical-name resolution as page wikilinks. The LSP warns when a relation target is missing; Reference Repairs projects both missing and ambiguous targets as `invalid_relation_target`. When one or more replacement candidates are available, the repair workspace can preview and patch the property occurrence with the selected page; otherwise it offers source navigation only. It does not enforce `many = false`, because cardinality remains an advisory schema warning.

See [relation repair](/docs/links-search-graph-and-repair#relation-repair) for the six issue classes, exact preview, stale-conflict, and one-at-a-time apply semantics.

## Failures and conflicts

Base files are parsed independently so one broken file does not poison the registry:

- Invalid TOML prevents that base from being evaluated. `/bases` still reports a diagnostic and the file path so you can repair it manually and reload.
- An invalid property declaration is dropped, while valid declarations and the rest of the base remain available with a diagnostic.
- Presentation entries with a blank field, a present blank label, a blank view-label value, or a repeated canonical preview identity are errors at their addressed paths. Unavailable custom properties and unknown explicit `sys.` references remain warnings.
- Other structural or type-invalid definitions produce addressed errors—for example, duplicate view names, an unsupported layout, a non-orderable comparison, or an aggregate without a compatible field. Property shadowing and undeclared-property references remain warnings.
- Some semantic errors are detected only when a view is evaluated. The saved table replaces its grid with the view error; the unsaved preview shows the error without discarding the draft.

If a base does not appear, check that it is directly under `<vault>/bases/`, ends in `.base.toml`, contains `name`, and has valid TOML. If `/bases/<slug>` says the base has no views, add at least one `[[views]]` entry. If date or number comparisons behave unexpectedly, verify the page uses native TOML values rather than quoted strings and that the property has the corresponding declaration.

V1 supports table layout only. Unsaved preview requests are capped at 100 rows; saved grouped views cap displayed rows in each group at 50 while retaining the true group total. These limits do not change the non-owning model: pages can match any number of bases, and removing a base never removes pages or page properties.

## Privacy

`.base.toml` definitions are plaintext. Page frontmatter properties and
relation values are plaintext, and index projections of that metadata are
plaintext. Base membership, filtering, grouping, aggregation, LSP completion,
and relation diagnostics can therefore reveal those values to any client or
process that can read the vault or its running server.

Protected folio bodies do not contribute body-derived word counts, FTS body
text, block rows, or body-link topology to the index; previously indexed
body-derived data is removed when a folio becomes protected. Its frontmatter
remains available to Bases, including title, kind, project, declared
properties, and relations, because protected-page encryption covers the body
rather than frontmatter. Do not place secrets in Base definitions or
frontmatter and assume body protection hides them.

Protected-page frontmatter can still participate in Base membership and saved tables, but the generic link/tab Base projection is suppressed in full. This prevents even otherwise plaintext projected frontmatter from appearing in a protected page's passive preview card.
