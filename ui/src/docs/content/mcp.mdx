`clep mcp` is a stdio Model Context Protocol server for agent hosts. It does
not open the vault itself: every `vault_*` tool proxies to the HTTP API of a
running `clep serve`, preserving that server’s revision checks, path locks,
link rewrites, hooks, folder projection, and event notifications.

## Prerequisites

1. Put `clep` on `PATH`.
2. Select the intended vault with the normal app
   [configuration](/docs/configuration), then start `clep serve`.
3. Register the stdio command with the MCP host. This repository’s `.mcp.json`
   has the required shape:

   ```json
   {
     "mcpServers": {
       "clepsydra": {
         "command": "clep",
         "args": ["mcp"]
       }
     }
   }
   ```

   Claude Code reads a project `.mcp.json`, or can register the same command
   globally with `claude mcp add clepsydra -- clep mcp`. Other MCP hosts need
   an equivalent command/arguments entry.

The MCP process and `clep serve` must resolve the same `config.toml`. Lookup is
`./config.toml` → `$XDG_CONFIG_HOME/clepsydra/config.toml` →
`$HOME/.config/clepsydra/config.toml`. Run `clep config path --trace` when the
selected vault is unclear.

## Workflow

### Connect to the running server

By default, `clep mcp` accepts only a configured loopback host such as
`localhost`, `127.0.0.1`, or `::1`. A non-loopback `[server].host` is refused
because the agent would operate on a remote vault; `clep mcp --allow-remote`
is the explicit override. Bind-all values are still considered non-loopback
for this safety check, even though the HTTP connect target is normalized to
`localhost`.

The URL scheme and port come from `[server]`. Plain configuration uses
`http://<host>:<port>`. When `[server.tls].enabled = true`, MCP uses HTTPS and
adds the configured or auto-generated server certificate as a trusted root.
Start `clep serve` once to generate automatic mkcert files before starting MCP.
TLS verifies the server and protects transport; it does not add an agent login.

### Choose the narrowest tool family

| Family | Tools | Use |
| --- | --- | --- |
| Discover and read | `vault_search`, `vault_get_page`, `vault_list_pages`, `vault_tree`, `vault_links`, `vault_tags` | Locate a page before acting; inspect content, structure, graph, and vocabulary. Oversized `vault_get_page` bodies are truncated and flagged. |
| Create and edit | `vault_create_page`, `vault_update_page`, `vault_edit_page`, `vault_append_page` | Create in one projected mutation; replace whole fields; exact-match a body span; or append to the page/a heading section. |
| Capture | `vault_journal_capture`, `vault_ai_journal_capture`, `vault_capture_conversation` | Add a fleeting entry to the user's journal or the AI journal, or capture complete visible conversation turns. |
| Task Board | `vault_board`, `vault_task_create`, `vault_task_update`, `vault_cycle_create`, `vault_cycle_update` | Inspect the board, create or update Tasks, and create or atomically close and carry over Cycles. |
| Organize | `vault_assign`, `vault_move_page`, `vault_folder` | Declare kind/project, explicitly move a page, or create/move/delete folders. |
| Page lifecycle | `vault_archive_page`, `vault_list_rubbish`, `vault_get_rubbish_item`, `vault_restore_page`, `vault_purge_page`, `vault_empty_rubbish` | Archive without rewriting links; inspect retained items; restore to the original path; or permanently purge one/all retained items. |

Search before creating. Prefer `vault_edit_page` for a targeted unique body
change, `vault_append_page` for additive capture, and `vault_update_page` only
when replacing a whole field is intentional. Prefer `vault_assign` for
kind/project filing; it computes the projected location. `vault_move_page` is
for an explicit destination that assignment cannot express.

### Author pages safely

Before creating a page, search with `vault_search` for an existing page and
extend it instead of duplicating it.

| Action | `ai-generated` | Tool |
| --- | --- | --- |
| Author standalone page | required | `vault_create_page` |
| Edit/append existing page | unchanged | `vault_edit_page` / `vault_append_page` |
| Journal capture | not added for authorship alone | `vault_journal_capture` |
| AI journal capture | not added for authorship alone | `vault_ai_journal_capture` |
| Conversation capture | not added for authorship alone | `vault_capture_conversation` |

Standalone pages must declare their real Kind and project in
`vault_create_page`. Use `vault_assign` to refile existing pages by project
rather than inventing folders. Substantial project documentation must
wikilink its project or hub page.

Errors are written for agents: active-page 404s suggest `vault_search` because
the page may have been refiled, while missing retained items stay within the
Rubbish Bin workflow. Stale-write 409s say re-read and retry. Restore conflicts
retain the archived item and distinguish an occupied original path from
changed retained bytes.

Move preview is read-only and is a snapshot, not a reservation. Re-read before
the real mutation. Bulk assignment is all-or-none. Recursive folder deletion
is a separate permanent operation; folder contents do not enter the Rubbish
Bin.

### Task Board

The board tools mirror the Task Board HTTP API. Use display labels in
agent-facing prose and persisted values in MCP calls: Inbox (`INTAKE`), Ready
(`TRIAGE`), In Progress (`FIELD`), Review (`REVIEW`), and Done (`SEALED`).
Priorities are P0 Critical, P1 High, P2 Medium, and P3 Low. `vault_board`
returns Projects through the legacy `operations` response field.
Legacy response fields remain unchanged. The raw `columns[].label` /
`columns[].sub` pairs are `INTAKE`/`unfiled`, `TRIAGE`/`staged`,
`IN-FIELD`/`active`, `REVIEW`/`qa / seal`, and `SEALED`/`closed`. Derive the
display label from `columns[].id` using the persisted status mapping above.
`tasks[].checks` is `[done, total]` Checklist Item counts.
`tasks[].link` and `operations[].dossier` contain Related Page values.

Create Tasks with `vault_task_create` rather than `vault_create_page`: the
board reserves the next `TSK-NNNN` code and files the page under
`tasks/<project>/`. Status defaults to Inbox (`INTAKE`), priority to P2 Medium
(`P2`), and the `body` wire field becomes the Task Description with Checklist
Items as `- [ ]` Todos beneath it. The `ai-generated` tag requirement applies
to LLM-authored Tasks.

The update tools accept a code (`TSK-0012`, `S-13`), a vault path, or a page
UUID; look codes up with `vault_board`. On `vault_task_update`, title, Project,
status, priority, and tags update when present. `clear_project: true` clears
the Project. Cycle, assignee, estimate, due, blocker reason (`hold`), and
Related Page (`link`) are tri-state: absent keeps the value, `null` or `""`
clears it, and a value sets it. A non-empty `hold` value means Blocked. The
Cycle sentinel `"BACKLOG"` moves a Task to Backlog.

Cycles cannot be created Closed: `vault_cycle_create` accepts Planned
(`PLANNED`, the default) or Active (`ACTIVE`). Close a finished Cycle with
`vault_cycle_update` by setting `state: "CLOSED"`. Pass `carry_to` to move
unfinished Tasks: `"BACKLOG"` moves them to Backlog, while a Cycle code such
as `"S-14"` reassigns them. `carry_to` is valid only with `state: "CLOSED"`;
without it, Tasks remain in the closed Cycle.

### Capture into a journal

Two capture tools write to two separate daily streams. `vault_journal_capture`
appends to the user's own journal (`journals/`) and is for the user's own
writing only — call it when the user explicitly asks for a journal capture,
never on the agent's own initiative. `vault_ai_journal_capture` appends to the
AI journal (`ai-journals/`) and is the default destination for agent-initiated
notes, work logs, session summaries, and asides; it never writes to the user's
own journal. Neither call adds the `ai-generated` tag: a capture is not
standalone authorship.

Both tools take `content` and create today's page on first write if it does
not exist yet. `vault_ai_journal_capture` also takes an optional `author`, a
single line of 1-64 characters (for example `claude-code`), rendered as an
entry prefix: `- HH:MM — [author] content`. Without `author`, the entry omits
the bracket. For both tools, plain prose becomes a timed list entry; an
existing list item, Todo, heading, blockquote, or code fence passes through
verbatim and unattributed, exactly as human captures do.

The AI journal is excluded from Agenda and from the human journal's
`carried_forward` Todos in both directions: an AI journal capture never
surfaces as agenda work, and reading it back returns no carried-forward list.

### Capture a conversation

Use `vault_capture_conversation`, not generic page creation. The request
requires a non-blank `title` and a non-empty ordered `turns` array whose roles
are exactly `user` or `assistant` and whose content is complete visible
Markdown. Optional `source_turn_id` and RFC 3339 `timestamp` values must come
from the host. `host_conversation_id` requires `provider`.

The host must supply every complete visible user/assistant turn in source order,
verbatim. Clepsydra cannot fetch missing history and does not accept hidden
prompts, tool traces/results, attachment contents, summaries, or placeholder
turns. With provider plus host ID, later calls append only an exact unseen
suffix; truncated or divergent history conflicts. Without the host ID, every
call creates a new Folio. See
[Codex and Conversation Capture](/docs/codex-and-conversation-capture#capture-or-append-a-visible-conversation)
for Read/Edit and protection behavior.

The compact request contract is:

| Field | Required | Meaning |
| --- | --- | --- |
| `title` | yes | Non-blank title used if a Folio must be created. |
| `turns` | yes | Non-empty, source-ordered complete visible turns. |
| `turns[].role` | yes | Exactly `user` or `assistant`. |
| `turns[].content` | yes | Non-blank visible Markdown, verbatim. |
| `turns[].source_turn_id` | no | Stable host turn ID, when the host exposes one. |
| `turns[].timestamp` | no | Host-supplied RFC 3339 timestamp. |
| `provider` | no | Normalized host provider; required with `host_conversation_id`. |
| `host_conversation_id` | no | Stable host chat ID; hashed for identity lookup and never stored raw. |

The response contract and outcomes are:

| Field | Meaning |
| --- | --- |
| `path` | Vault-relative conversation Folio path. |
| `page_id` | Stable Folio UUID. |
| `operation` | `created`, `appended`, or `unchanged`. |
| `appended_turns` | Turns written by this call: all on create, only the new suffix on append, zero when unchanged. |
| `skipped_turns` | Existing exact-prefix turns not rewritten; all submitted turns when unchanged. |
| `warnings` | Non-fatal capture warnings; currently returned as an array. |

`created` returns HTTP 201 for a new Folio. `appended` and `unchanged` return
HTTP 200. A conflict has no success response and writes nothing.

## Failures and conflicts

- **Server unreachable** — MCP reports the configured base URL and tells the
  agent to start `clep serve`. Confirm the server and MCP process resolve the
  same config, host, port, and TLS mode. Follow
  [Troubleshooting](/docs/troubleshooting).
- **TLS certificate cannot be read or verified** — start the TLS server once so
  automatic certificates exist, or correct both configured certificate paths.
  Do not disable TLS to hide a remote trust failure.
- **`404`** — a page may have moved after assignment. The tool error recommends
  locating it with `vault_search`; do not keep writing the stale path.
- **`409` stale revision** — re-read with `vault_get_page`, reconsider the
  intended change, and retry. Only `vault_update_page`, `vault_edit_page`, and
  `vault_append_page` read and send `expected_revision`; the server checks it
  under the mutation path lock. `vault_create_page` instead uses atomic
  no-overwrite creation. Assignment and move operate against the mutation
  coordinator's current server state; they do not send a revision copied from
  an earlier MCP page read.
- **`409` restore conflict** — an occupied original path, changed retained
  item, or already-committed permanent-deletion cleanup blocks restoration.
  Inspect the item again; move an occupied active page, refresh changed state,
  or retry `vault_purge_page` when the server reports deletion in progress.
- **Validation or protocol error** — invalid paths, kinds, projects, tool
  fields, JSON, or unexpected response bodies are returned to the agent.
  Correct the request rather than guessing.
- **Protected content** — MCP has no unlock, protect, or unprotect tool.
  `vault_get_page` can report metadata and the stored age-armored body, not
  decrypted plaintext. Body edits cannot operate on the hidden plaintext, and
  conversation capture refuses to append to a protected matching Folio.

`vault_append_page` alone performs one targeted stale-write retry. Other
mutations do not silently replay, and no tool should turn an uncertain error
into an assumed success.

## Privacy

The MCP host and its agent can see every tool argument and result. Unprotected
titles, metadata, bodies, search snippets, links, tags, folder names, and
conversation turns are plaintext. They cross stdio between the host and
`clep mcp`, and cross HTTP between `clep mcp` and `clep serve`. Loopback HTTP is
still unencrypted transport; HTTPS encrypts that hop.

The MCP HTTP client sends no bearer token, password, or other application
credential. Loopback reachability is the default trust boundary. Treat every
local process allowed to drive the MCP host and every process able to reach the
configured API as trusted with the accessible vault data. For a remote server,
`--allow-remote` records intent but provides no user authorization; use HTTPS
and a separately controlled network boundary.

Protected Folio bodies remain ciphertext because MCP has no browser decryption
identity. Filenames, paths, titles, tags, projects, encryption descriptors,
conversation provider and ledger hashes, and attachment metadata remain
plaintext. MCP tools do not make unprotected pages, attachments, archives, or
backups encrypted.
