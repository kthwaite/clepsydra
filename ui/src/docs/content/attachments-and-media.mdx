Attachments are vault-wide files stored beneath the configured attachment
folder, `_attachments` by default. Folios can associate files through frontmatter
and reference them in Markdown. Removing a reference does not remove the
association or move the attachment bytes.

## Prerequisites

- Open an editable Folio in `/workspace` and expand **Manage attachments** under
  **Attachments**.
- A protected Folio must be unlocked before its attachment manager can inspect
  the decrypted Markdown or insert a reference.
- The server must be able to write the vault's `vault.attachment_folder`.
  Attachment URLs use `/api/vault/attachments/<attachment-path>`.

## Workflow

### List and open attachments

**Manage attachments** loads the complete attachment inventory, including files
in attachment subfolders. Entries are sorted by path and show the filename and
byte size. Choose the filename to open the served file in a new browser tab.
The server reports a MIME type inferred from the attachment path and otherwise
uses `application/octet-stream`.

### Page attachments and the image gallery

Files associated with a Folio appear in an **Attachments** section below its
body unless the body already links to or embeds them. An empty section is hidden.
Images have thumbnails; other files have **Open** and **Download** links.

Choose an inline image or a footer thumbnail to open the shared lightbox. Use
the previous/next buttons or **Left/Right arrows** to navigate, and **Escape**
to close. The viewer shows the filename and position. Zoom and pan reset when
switching images; closing restores focus to the image that opened it.

The gallery lists referenced images in document order, then remaining associated
images in attachment order. Each file appears once, and navigation wraps around.
Reference detection recognizes Markdown links, images, and reference-style links,
including attachment URLs and vault-relative paths. Code examples are ignored.

Uploads, **Insert**, and **Attach to page** record the association in the note:

```toml
attachments = ["diagram.png", "research/report.pdf"]
```

These are paths relative to the configured attachment folder, not URLs. Existing
vault files are not assigned to a page by filename: choose **Show all attachments**
and **Attach to page** to associate one without inserting anything into the body.
The manager's page view includes both associated and referenced files.

Adding an inline reference hides the matching footer entry. Removing that
reference reveals the entry again if the file is still associated. To remove an
association without deleting the file, edit the note's frontmatter externally.
The page update API also accepts an `attachments` array: omitted preserves the
current associations; `[]` clears them.

### Drop files into a Folio

Drag one or more local files onto the editable Folio body. A caret marks the
insertion position and a floating label identifies the file or file count.
Drop to upload the files in order and insert their references at that position:
images render inline; other files become links. Successful uploads automatically
refresh and expand **Manage attachments**, including reopening a collapsed
desktop details sidebar. No separate **Upload** or **Insert** click is needed.

You can continue editing while uploads run; the drop position follows those
edits rather than the current cursor. Leaving the page, replacing its editor,
or making it read-only cancels pending insertion and stops subsequent uploads.
A request already sent to the server may still store its file. Successful uploads
associate files with the current page while that upload session remains active.
If you delete the insertion position, associated files remain available in the
footer. Files uploaded after leaving the page may remain unassociated; find them
through **Show all attachments** and choose **Attach to page** or **Insert**.

Protected Folios require a separate plaintext-storage acknowledgment before
each file uploads. Cancelling stops the remaining batch; earlier successful
uploads still receive references. Failed files show their names and errors
without inserting broken references, while other files continue. A filename
collision never overwrites the existing attachment.

File drops are disabled in read-only bodies. Ordinary text and internal editor
drags retain their existing behavior. The **Upload** picker below remains the
keyboard-accessible alternative.

### Upload a file

1. Choose **Upload** and select one file.
2. On a normal Folio, Clepsydra stores and associates the file without inserting
   a body reference. It appears in the footer automatically. Choose **Insert**
   when you want it inline instead.
3. On a protected Folio, review the per-upload plaintext disclosure. Cancelling
   stores no file and inserts no reference. Acknowledging uploads the file and,
   after success, associates it and inserts its Markdown reference into the Folio.

Uploads use the selected filename as the attachment path. The server creates
missing attachment subfolders, installs the upload without replacing an
existing file, and requires the multipart field
`plaintext_acknowledged=true` for every upload.

### Insert or copy a reference

Choose **Insert** on an existing entry to associate it with the page and insert
at the current Folio selection. **Attach to page** associates it without insertion.
On a protected Folio, each insertion or association of an already stored attachment
opens a separate plaintext disclosure; an acknowledgment from an earlier action
is never reused.

Clepsydra generates an image reference for `avif`, `bmp`, `gif`, `jpg`, `jpeg`,
`png`, `svg`, and `webp` paths:

```markdown
![diagram.png](/api/vault/attachments/diagram.png)
```

Other files use an ordinary Markdown link:

```markdown
[notes.pdf](/api/vault/attachments/notes.pdf)
```

**Copy Markdown for _filename_** copies the same generated reference without
editing the Folio.

### Delete an attachment

Choose the trash control, then **Confirm delete _filename_**. Deletion removes
the stored file only. It does not scan or rewrite Folios: existing associations
and Markdown or HTML references remain in place. Missing files disappear from
the footer, but body references may become broken. Cancel before confirmation
to leave the file untouched.

### Audit stale references on protected Folios

While **Manage attachments** is open for an unlocked protected Folio, the
browser compares recognized attachment links and images in the decrypted
Markdown with the successfully loaded inventory. **Plaintext attachment
references** lists recognized paths that no longer match a stored file.

This is a client-only, best-effort audit. It recognizes Markdown links and
images that target Clepsydra attachment URLs. It ignores raw HTML, code,
malformed or unresolved links, and non-attachment destinations. If inventory
loading fails, no stale-reference warning is shown. No warning is therefore not
proof that every reference is valid. The browser sends neither decrypted body
text nor its extracted reference inventory to the server for this audit.

## Failures and conflicts

- Uploading to an existing attachment path returns HTTP 409 and does not replace
  the stored file. Rename the local file or choose a different path.
- An invalid vault-relative path, malformed multipart request, missing file,
  missing/false acknowledgment, duplicate field, or unknown field is rejected
  without installing the upload.
- A failed upload displays **Could not upload _filename_** and inserts no
  reference. Retry after correcting the server, path, or network problem.
- If the inventory fails to load, the manager reports the error and suppresses
  the protected-page stale-reference audit rather than presenting incomplete
  results as clean.
- Fetching or deleting a missing attachment returns 404. Deleting succeeds only
  for a file, not a directory.
- Deletion does not check backlinks or references. Restore the file or repair
  every stale reference yourself.

For protected Folios, the plaintext acknowledgment has a narrow boundary. It
covers each new upload and each frontend insertion or association of an already
stored file. Existing references remain available to the best-effort audit while
the protected Folio is unlocked; they are not retroactively acknowledged or
removed. The server enforces the upload field, but reference confirmation is a
Clepsydra-frontend safeguard. A custom client can insert a reference without
that confirmation and can construct valid encrypted ciphertext whose plaintext
the server cannot inspect. The acknowledgment is disclosure, not encryption,
authorization, or proof that ciphertext contains no attachment references.

## Privacy

Attachment bytes are always plaintext. Filenames, attachment paths, reported
MIME types, and sizes are also plaintext and can disclose the subject or
content. Page associations in `attachments` frontmatter are also plaintext,
including on protected Folios. Only references inside the encrypted body are
encrypted; the files remain plaintext beneath the attachment folder and are
served by their plaintext URLs.

Use non-revealing filenames, remove sensitive metadata from files before
uploading, and protect access to the vault and HTTP session. Body encryption is
not a substitute for encrypting the attachment itself.
