# Multi-resource mutation audit

## Method and scope

This inventory was completed before changing tests or production code and expanded before the review-fix tests. The search follows every production caller of `MutationCoordinator` and `MutationPlanner`; `fs::rename`, `fs::remove_file`, `fs::remove_dir_all`, directory creation, direct writes, `OpenOptions`, `atomic_create`/`atomic_replace`, temporary-file/bundle publication, attachment no-replace install, filesystem-mutating child processes, and CAS `store`/`increment_ref`/`decrement_ref` calls. API handlers and every offline CLI/watcher entry point are listed below. SQLite indexes and the feed database are included when a filesystem mutation treats them as a second resource; read-only routes and derived-index-only rebuilds are excluded.

Classifications mean:

- **Batch coordinator**: every file in the logical unit is represented by one durable `BatchMutationCommand`; failure rolls back all published intents, and a post-filesystem index failure retains recoverable transaction state.
- **Single-file coordinator**: one authored file is the logical commit; publication and index reconciliation are serialized and compensated by `MutationCoordinator`.
- **Single-resource atomic publication**: one file or directory entry is the complete authored resource. No cross-file atomicity is claimed.
- **Compensated external-resource transaction**: resources cannot share one filesystem transaction. The implementation commits one resource and explicitly compensates it if the other resource fails; compensation errors remain actionable.
- **Per-item commits**: a loop is deliberately not all-or-none. Each item is independently committed and represented by one result entry.
- **Derived-resource reconciliation**: the authored file is authoritative and the second store is rebuilt/reconciled rather than presented as an atomic peer.

## Conclusions before Task 6 code changes

1. Page move/delete, folder move, watcher reconciliation, cycle carryover, and bulk assignment are correctly classified as durable batch-coordinator operations. They must not gain secondary executors or per-path success responses.
2. Archive ingestion necessarily spans the vault filesystem/index and the independent CAS SQLite/blob store. Its valid model is explicit, idempotent compensation with retained primary and cleanup errors; it must not be described as cross-resource filesystem atomicity.
3. Zotero and BibTeX endpoints expose ordered per-item `results`, so their valid boundary is one independently reported item per commit. No endpoint contract declares an all-or-none import.
4. Task 6 therefore adds deterministic post-CAS and post-page-publication archive proofs and an item-two Zotero failure proof. Production changes are permitted only if those tests expose a mismatch between the classifications above and observable state/response behavior.
